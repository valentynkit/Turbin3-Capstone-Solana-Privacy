# R1 — adversarial crypto/privacy review of the payout rail (2026-09-14)

TL;DR: the derivation tree looks sound on paper and the stealth math survived every attack I tried; the two things that will actually hurt are a permissionless griefing DoS on the token-2022 pending-balance counter with no recovery path, and the fact that "recipient hidden" depends entirely on client discipline the program does not enforce.

Builds on `research/2026-09-11-skeptic-stealth-confidential.md` (F1 consolidation, F2 payer key knowledge) and `research/2026-09-11-crypto-derivation-review.md`. I do not repeat those, only extend where new.

## CRITICAL

**C1. Third-party pending-balance-counter griefing bricks a stealth account, with no reset path.** [likely]
Target: `design.md` instructions table (`fund`, `sweep`) and `decisions.md` "apply-pending only inside sweep so nobody can poison the decryptable-balance cache."
Token-2022's confidential `Transfer` credits a destination token account without the destination's authorization — standard permissionless SPL crediting — and increments `pending_balance_credit_counter` against a fixed `maximum_pending_balance_credit_counter` (65536, `token2022-mechanics-verified.md`). Once `open`+`configure` run, the StealthAccount's E/view_tag/P (and therefore its token account address) are public. Anyone, not just the payer, can send confidential dust into that account before the payer's real `fund` lands. If Token-2022 rejects further credits once the counter tops out (standard behavior for this extension), the payer's legitimate funding transaction fails. The only way to reset the counter is `ApplyPendingBalance`, and the design restricts that to inside `sweep`, which only P (the recipient) can call, and sweep is presumably gated on a funded state that was never reached. Net effect: an attacker who watches `getProgramAccounts` for freshly opened StealthAccounts can permanently brick any of them for a few lamports, before the real payment ever arrives, with no on-chain recovery.
This is the direct cost of fixing the poisoning issue (`decisions.md`) by restricting `ApplyPendingBalance` to sweep-only: closing one hole opens another. The fix should not reopen poisoning to third parties. Cheapest fix: let the **payer** (who has the account's AES/ElGamal keys by design, so can compute a correct `decryptable_available_balance`) call an `unstick`/`apply` instruction outside of sweep, gated to the stored payer identity, or require `open`+`configure`+`fund` to land atomically in one transaction so there is no public window before real funds arrive. Spike: read `process_transfer`'s counter check and `EmptyAccountInstruction`'s preconditions in token-2022's confidential_transfer processor to confirm the max-counter failure mode and whether a griefed, never-applied account can even be closed to reclaim rent.

**C2. Raw-scalar nonce must bind to the message, not just to p — the doc gets this right, but a one-word implementation slip is catastrophic and indistinguishable from the safe version at a glance.** [open]
Target: `crypto.md` "Signing with the one-time key" and the `nonce-seed` line in the derivation tree.
The spec correctly calls the Expand output a "hash prefix," meaning it must be combined with the message per-signature (`r = H(prefix || M) mod L`), which is exactly how EdDSA gets nonce-per-message safety without external randomness. If an implementation instead used that 32-byte output directly as `r` (skipping the message-dependent hash), then a retried sweep after a dropped transaction — same P, different blockhash, therefore a different message — would produce two signatures sharing one `R`, and standard nonce-reuse algebra recovers p for anyone who observes both signatures on-chain (not just the payer — any chain watcher). This is precisely the class of bug RUSTSEC-2022-0093 and "Taming the many EdDSAs" catalogue for hazmat APIs. The design attack-surface item ("what happens if the same P signs two different sweep transactions") is answered correctly in the doc, but nothing currently forces the implementation to stay correct. Cheapest fix: a mandatory regression test asserting R differs across two different messages signed by the same derived p, added to the reviewer checklist in `crypto.md`, before this ships.

## MAJOR

**M1. Sweep-destination reuse is a client convention, not a program invariant.** [verified against design.md]
`design.md`'s `sweep` guard is "P must match the stored key; nonce; state becomes swept" — nothing constrains the destination account. `plan.md` Q4 records the destination-reuse question as still open, recommendation "refuse by default" at the client only. This means the F1 consolidation mitigation from the 09-11 skeptic review has zero on-chain enforcement: any alternate client, a buggy wallet, or a future SDK version can silently sweep to a reused address and nothing rejects it. `privacy.md`'s "recipient hidden" claim is therefore conditional on every implementation forever choosing not to do the convenient thing. Fix is cheap relative to the risk: either the program tracks a per-recipient "used destinations" set (expensive, probably not worth it) or, more realistically, document loudly in `design.md` that this is client-policy-only and cannot be a security claim, and consider a lightweight on-chain check (e.g., destination account must not already hold a `swept` marker owned by this recipient's spend key) as a phase-two item.

**M2. Underfunded P forces a self-funded top-up that links the recipient's real wallet to the stealth account.** [likely, new — not in privacy.md's leak table]
The payer funds P's system account with "fee dust" (`design.md` `open`). If that dust is insufficient for the sweep's actual cost (ApplyPendingBalance + confidential Transfer out + closes, ~5 transactions of proof context accounts per `token2022-mechanics-verified.md`), the recipient's only recourse is to send more SOL to P from a wallet they control, since P is an ordinary System address anyone can top up. That top-up transaction is public: it directly connects an identifiable funding wallet (a CEX withdrawal address, an existing named wallet) to P, and from there to the stealth account and the eventual sweep destination — the exact deanonymization the whole construction exists to prevent. `privacy.md`'s artifact table lists "P's system account funded by the payer" as a non-leak; it does not list a *second* funder. Cheapest mitigation: the payer overprovisions dust generously (cost is trivial, ~0.0003 SOL per extra proof-context round) and the client warns loudly rather than silently succeeding with tight margins; document this explicitly as a residual leak either way.

**M3. Torsion-free `B_spend` is a recipe in crypto.md, not a specified enforcement point in the registry program.** [open]
`design.md`'s Registry account only lists fields (`spend_pub, scan_pub, version`); the `register` instruction has no described validation step. `crypto.md`'s reviewer checklist says "torsion-free B_spend" must be checked at registration, but design.md never says the `register` instruction performs it. Since nothing yet exists, this is not a bug, just an unpinned requirement that could slip. Cheapest fix: add the check explicitly to `design.md`'s `register` row before implementation starts, so it's a tracked requirement rather than a fact that lives only in the crypto recipe.

**M4. Sweep amount and partial-sweep semantics are undefined, and that ambiguity weakens two other claims at once.** [open]
`design.md`'s `sweep` row doesn't say whether the confidential Transfer out must move the entire available balance. `close` requires `EmptyAccount`'s zero-balance proof, which structurally forces a full sweep before close — but nothing stops a design (or future feature) where `sweep` takes an amount argument and can be called more than once before the account is emptied. If that ever happens: (a) it interacts with C1's counter exhaustion in new ways, and (b) it breaks the compliance claim in `research/2026-09-11-compliance.md` that disclosing one payment's key discloses exactly one payment — a multi-sweep account would let a disclosed key reveal several sub-transfers instead of one. Recommendation: pin "sweep always moves the full available balance, one shot" as an explicit invariant in `design.md`, since it's currently true only by omission.

**M5. The BIP-352 citation over-claims precedent for the four-way derivation.** [note, documentation accuracy]
`crypto.md`: "Why: RFC 5869 says distinct info under a PRF gives computationally independent outputs. Binding E and an index k follows BIP-352." BIP-352 only ever derives one value (`t_k`) from the ECDH secret; it has no precedent for deriving a tweak, a view tag, confidential-balance IKM, and a signing-nonce prefix from the same secret. That's fine cryptographically (RFC 5869 §3.2's multi-`info` independence claim covers it, same pattern as a TLS 1.3 key schedule), but citing BIP-352 for it implies a battle-tested precedent that doesn't exist for this exact composition. This is the piece Q1's external review most needs to look at — worth saying so plainly rather than borrowing BIP-352's credibility for it.

## MINOR / NOTE

**N1. Recipient scanning via `getProgramAccounts` leaks the scanning IP to the RPC provider.** [note, standard limitation]
View tags only cut client-side trial decryption, not the need to fetch the whole StealthAccount set (a recipient can't ask an RPC to filter by "accounts whose view tag matches my key" without revealing which tag matters to them across payments, since the tag differs per payment). Same problem BIP-352 light clients and Zcash light wallets have; not a design defect, just missing from `privacy.md`'s leak table. Mitigation: run your own RPC, or a light-client relay, same as those ecosystems.

**N2. Batch timing lets an observer fully enumerate a payer's headcount even though identities stay hidden.** [note, reinforces an accepted residual]
If a payroll run opens+configures N StealthAccounts from one payer, one lookup table, in a tight time window, an observer learns "payer X paid exactly N people this cycle" with certainty, even without breaking any individual link. `privacy.md` already accepts payer-side timing and program fingerprinting as residuals; this is a specific, concrete instance (headcount is fully countable) worth naming rather than leaving implicit.

## What survived

- All-zero `S` rejection, combined with standard clamped X25519 for the scan side, correctly neutralizes small-subgroup confinement from a malicious payer choosing a torsion `E` — clamped X25519 collapses any low-order input to zero, and zero is already rejected. [likely]
- A malicious payer cannot choose `E` to make `P` collide with or relate to a chosen target key; doing so requires a preimage against the HKDF/Expand output used for `t`, a ~256-bit search. [likely]
- The payer cannot forge a sweep: it never learns `p` because `b_spend` never touches `S`, only `B_spend` does (as the constant being tweaked). [verified by construction, assuming domain separation holds]
- The payer cannot decrypt the destination side of a sweep: the outgoing Transfer's destination handle is encrypted under the destination account's own ElGamal key, which the payer never derived. [likely]
- Multi-device recipients need no coordination: `p`, `S`, and every derived value are fully deterministic from `b_spend`/`b_scan` plus public `E`, so two devices independently arrive at the same values. [verified against crypto.md]
- Per-payment auditor key disclosure is scoped to exactly one payment, not the recipient's whole history, given the one-time-account invariant holds and distinct Expand labels aren't correlatable to each other without the PRK. [likely, contingent on M4 and the still-open Q1 review]

## Brief refinements

`docs/brief.md` should change in three places; I am not editing it.

1. Section 6, "Payer holds that one account's key" bullet — currently reads as if the payer's only capability is passive knowledge. Add a clause: the payer can also delay or permanently grief a payment by underfunding the sweep-fee dust (forcing a self-linking top-up, M2) or by leaving the standard third-party dust-griefing window open before it patches C1. Proposed addition after the existing sentence: "A payer — or anyone watching for newly opened accounts — can also delay or permanently block a payment before it lands, by underfunding P's sweep fee or by exhausting the account's pending-balance counter before the real transfer arrives; this is a griefing/DoS risk, not a fund-theft risk, and needs a program-level fix before launch."

2. Section 10 claims table, row "Only the recipient can sweep; the payer cannot | verified by construction." This is true narrowly (fund movement) but reads as a stronger safety claim than the construction gives. Proposed rewording: "Only the recipient can move funds out; the payer cannot forge a sweep | verified by construction" with a new row: "The payer or a third party can block a payment before it is swept | open, needs a program fix (see crypto review R1)".

3. Section 6, "Consolidation re-links" bullet — currently states the sweep-to-fresh-account rule as if it were a guarantee. It is client policy only (M1); nothing on-chain enforces it. Proposed addition: "This is enforced by the client today, not by the program; an alternate client or a bug can silently defeat it."
