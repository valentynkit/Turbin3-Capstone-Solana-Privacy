# R2 ops, cost, and delivery skeptic (2026-09-14)

TL;DR: the candidate fixes the atomicity and dust framing from round 1 but the lookup table math undercounts addresses by roughly 3x, and the "0.014 SOL on P" figure still has almost no room for priority fees on the one instruction that actually needs them (the range proof). Six of round 1's ten findings are only partly closed; two are untouched.

How to read: **[verified]** checked against a cited source in this repo's research. **[likely]** arithmetic over verified numbers, not independently re-run. **[open]** unresolved, needs a spike.

## Critical

**1. Lookup table capacity is overcounted by roughly 3x once P and the proof contexts are included.**
Target: "Lookup table lifecycle" implied by the candidate's "one v0 transaction with a per-run lookup table" for the combined payer tx. The back-of-envelope in this prompt (256 addresses, 2 PDAs per recipient, ~125 recipients/table) only counts the stealth PDA and the token-account PDA. It omits P itself (a fresh keypair per recipient, non-signer but still a writable account reference in the combined tx, since the payer's System transfer targets it) and the three Transfer proof-context accounts that the combined tx must reference by pubkey (candidate: "the three Transfer proofs go through context accounts"). That is 2 PDAs + P + 3 contexts = 6 addresses per recipient, not 2. With ~6 static entries (mint, payer's token account, Token-2022 program, System program, ZK ElGamal proof program, ComputeBudget program), capacity is (256-6)/6 ≈ 42 recipients per table, not ~125. At N=500 that is roughly 12 tables, not 4, each needing its own extend-and-warm cycle. This also weakens R2-3 (does the combined tx fit 1232 bytes): if the client decides not to put P and the contexts in the ALT because of this cap pressure, the combined tx carries them as 32-byte static keys instead, adding ~192 bytes back and making the byte-fit claim less likely to hold. **Fix (spike, before week 2):** enumerate every account the combined tx actually references, decide which are ALT-eligible (non-signer only), compute the real per-recipient address count, and re-run the 1232-byte estimate with that count. Exit criterion: a measured serialized transaction size, not "[likely; measure]".

**2. Money on P has no real margin for priority fees; the range proof alone can eat 3x the stated buffer.**
Target: "Money on P" section. Recompute from the candidate's own cited rent figures (mechanics-verified table): D rent 0.00416 + transient sweep-context rent (equality 0.00201144 + 3-handle validity 0.00357048 + range U128 0.002958 = 0.00853992) = 0.01270 SOL. Base fees for six to seven transactions at 5,000 lamports/signature, counting the real signer sets (create-D-and-configure needs both P and D_owner; each of the three context-creation transactions needs P plus the fresh context keypair signing its own creation), come to roughly 50,000-60,000 lamports (0.00005-0.00006 SOL). Sum: ≈0.01276 SOL. The candidate states "about 0.014 SOL," leaving ≈0.0013 SOL for priority fees and retries combined. R1 finding 3's own congestion scenario (10,000-50,000 microlamports/CU) puts a single VerifyBatchedRangeProofU128 instruction (200,000 CU, from mechanics-verified) at 0.002-0.01 SOL in priority fee alone, on top of its base fee, before any other instruction in that transaction is priced. Even the low end of that range (0.002 SOL) is 1.5x the entire implied buffer. This is the same gap R1 finding 3 raised, carried into the new numbers without being closed. **Fix:** publish "Money on P" as rent (recoverable) + rent (D, not recoverable) + base fees + priority-fee allowance as separate line items, sized from ops spike 4's measured distribution, not folded into one round number. Exit criterion: a formula the client can evaluate per-run against a live `getRecentPrioritizationFees` sample, not a constant.

## Major

**3. `open`'s instruction data is missing the field ConfigureAccount needs.**
Target: instruction table, row 2 (`open`). Folding ConfigureAccount's CPI into `open` still needs `decryptable_zero_balance` (36 bytes, AE-encrypted under the account's AES key) as input, because that key is derived from the shared secret the payer computed via ECDH for this specific stealth account, not a value the program can construct on-chain. The listed instruction data (E 32, P 32, view_tag 1, rent_refund 32, dust_lamports 8 = 105 bytes) has no field for it. Either it is missing from the table (add 36+ bytes, which also affects the R2-3 byte-fit question) or the design intends a fixed all-zero AE ciphertext, which would need the AE scheme to support a public, verifiable "this is zero" ciphertext without the key, unlikely for authenticated encryption. **Fix:** state explicitly whether `decryptable_zero_balance` is payer-supplied client-side data or a constant, update the instruction data list and the byte-size estimate accordingly. Cheap, no spike needed, just a doc fix plus a size recount.

**4. Context-account keypair determinism is unspecified, which breaks the resume story for exactly the accounts most likely to be orphaned.**
Target: "Batch resume" row in "What round 1 settled," and the journal design. The candidate carries forward "`e_i = HKDF(run_secret, run_id || i)`" for the ephemeral key only. Proof context accounts are described as "keypair accounts owned by the ZK ElGamal proof program" with no stated derivation. If they are randomly generated per attempt, a crash between generating the keypair and fsyncing it to the journal leaves an account whose address the client can never recompute, so it cannot be found again, closed, or its rent reclaimed except by a separate `getProgramAccounts` sweep for orphans owned by the ZK ElGamal proof program with authority = payer (a probe the design never names). If instead context keys are meant to be deterministic sub-derivations of `run_secret`, say so, because that is what "check on-chain state before every step" requires to actually be checkable. **Fix:** derive context keypairs the same way as `e_i` (e.g. `HKDF(run_secret, run_id || i || "eq"/"validity"/"range"/"pubkey")`), so resume never depends on journal survival for these accounts, only for the step marker.

**5. The journal's ambiguous-state handling is asserted, not enumerated, and the one case the prompt calls out (open-landed-but-Transfer-failed) needs an explicit atomicity claim, which does hold.**
Target: "Batch resume." Solana transactions commit all-or-nothing; a failing instruction anywhere in the combined tx reverts every effect in that tx, including the System creates and the funding of P [general Solana execution model, not independently re-cited here]. So "open landed but Transfer failed inside the same transaction" cannot happen as a partial state; either the whole combined tx lands with state = Live, or none of it lands and the StealthAccount PDA does not exist. That resolves cleanly. The cases that remain genuinely ambiguous and are not enumerated anywhere: (a) transaction sent, no signature status yet (poll `getSignatureStatuses`, wait); (b) blockhash's `lastValidBlockHeight` passed and no status found (safe to treat as did-not-land and retry, since fee is only charged on inclusion); (c) a context-creation transaction whose proof verification instruction failed (same atomicity argument as above, means the context account was never created, safe to retry with a fresh or re-derived keypair per finding 4). **Fix:** write these three cases into the design doc explicitly with the RPC calls used to distinguish them, and state journal contents precisely: run_id, recipient_index, step name, derived account pubkeys (recomputed, not stored, once finding 4 lands), transaction signature once sent, last_valid_block_height, outcome. State explicitly what must never be written: `run_master_secret`, any derived private scalar (ElGamal secret, AES key, P's raw signing key). Cheap, no spike.

**6. No stated concurrency bound or proof-generation timing means N=50/N=500 wall-clock cannot be computed, only guessed.**
Target: "Costs to publish," batch engine ("execute (bounded concurrency...)"). No published `solana-zk-sdk` timings for range-proof, ciphertext-validity, or equality-proof generation exist in any round-1 file [open, none of the four round-1 sources cite one]. The candidate also never states the concurrency bound the "bounded concurrency" execute phase uses. Any wall-clock table is therefore an assumption exercise; the table below states its assumptions and should not be read as a commitment.

| N | Proof gen (assumed 100 ms/proof, 8-way parallel) [open] | Context-creation txs (4/recipient, 1.5 s confirm, concurrency 8) [likely] | Combined tx (concurrency 8) [likely] | ALT extend + 1-slot warm-up (per table, ~42 recipients/table per finding 1) [likely] | Total, payer side only |
|---|---|---|---|---|---|
| 50 | ~15 s | ~47 s | ~9 s | 2 tables, ~16 s | ~1.5 min |
| 500 | ~150 s | ~470 s (~8 min) | ~94 s | 12 tables, ~96 s | ~13 min |

Recipient-side (6-7 more transactions per payment, same concurrency assumption) roughly doubles both totals if run in the same window. **Fix (spike, week 1):** measure `solana-zk-sdk` 8.0.0 proof generation on the actual dev machine for all four proof types at N=1 and N=50 (this is R1's own spike 1, apparently not yet run since the candidate still marks timings [open]); state the batch engine's concurrency bound as a config default, not an implementation detail left for later.

**7. The recipient-side floor check conflates two different failure modes, one of which still burns fees.**
Target: "Money on P," "the client refuses to start a sweep below a computed floor." Two distinct cases exist. (a) P's balance is below what the fee payer needs to cover base + priority fee: the runtime rejects the transaction before inclusion, no fee is charged, the client sees a simulation or send error and can retry after top-up with no loss. (b) P covers the fee but not the rent an instruction inside that same transaction needs to transfer (e.g., a context account's rent-exempt minimum): the transaction lands, the instruction fails, the whole tx reverts by atomicity, but the fee is still deducted because the transaction was included in a block. Case (b) is the death spiral R1 finding 4 described, and it is not prevented by a single "computed floor" unless that floor separately accounts for the largest single in-tx rent requirement, not just the total across the run. **Fix:** split the floor check into "can P pay this specific transaction's fee" (checked via simulation before every send) and "does P hold enough for every rent transfer inside this specific transaction" (checked against that transaction's account list, not the run total). Tell the recipient which one failed and by how much lamports, since only the payer (via crypto M2's link-risk warning) can top up P.

**8. The testing gate is still contingent on an unresolved question, and the Surfpool fallback's cost is unquantified.**
Target: "Testing" section, "LiteSVM is the functional gate [open: confirm the ZK ElGamal builtin runs in LiteSVM and Mollusk, ops 6]." This is R1 finding 6 restated, not answered; R1's own week-1 spike 2 (run one `ConfigureAccount` + `PubkeyValidityProof` through each harness) does not appear to have been executed between R1 and this candidate. If the builtin is absent from LiteSVM/Mollusk, every functional test involving a real proof moves to Surfpool. LiteSVM tests run in-process with no RPC round trip, typically single-digit to low-tens of milliseconds each; an embedded Surfpool instance is a real (if local) SVM runtime processing simulated RPC calls, plausibly one to two orders of magnitude slower per test [open, no benchmark run]. A 50-test suite going from under a second to tens of seconds materially changes the red-green-refactor loop the owner will run dozens of times a day. Separately, Mollusk CU benches with a CI assertion are realistic, not noise: Solana's compute metering is deterministic for fixed inputs, so an exact or tight-tolerance CU assertion in CI is a sound regression gate, not a flaky one; the only maintenance cost is updating the baseline when an SDK or program upgrade changes underlying CU constants. On the golden-byte question: mechanics-verified cites `spl-token-2022-interface-3.1.1`'s `extension/confidential_transfer/instruction.rs` for the Pod struct layouts and discriminants used to hand-encode; none of the round-1 files quote an actual instruction-builder function signature from that module, so "the interface crate builds those instructions off-chain" is [likely], not [verified], from what this repo has checked so far. **Fix (spike, week 1, unchanged from R1):** run the ConfigureAccount + PubkeyValidityProof case through LiteSVM, Mollusk, and Surfpool directly and time all three; separately grep the 3.1.1 source for a public `pub fn configure_account(...) -> Instruction` (or equivalent) in that module and cite the line if found.

## Minor

**9. No CU total for the combined transaction is published, though the margin looks comfortable.** Verified components (VerifyPubkeyValidity 2,600 + three CloseContextState 9,900) sum to 12,500 CU. Token-2022's own processing CU for InitializeImmutableOwner, InitializeAccount3, ConfigureAccount, and Transfer is still "not independently re-derived" per mechanics-verified's own open item; even a pessimistic 10x pad on the ~31k estimate used there (310k) plus PDA-derivation overhead in our program stays under 400k CU against the 1.4M cap, over 3x margin. Unlike round 1's concern, CU headroom was never really the risk; the byte-size cap is. Fix: one Mollusk bench per instruction (already planned) closes this without a spike.
