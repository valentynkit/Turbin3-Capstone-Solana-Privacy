# R1 — Ops, cost, and delivery skeptic (2026-09-14)

TL;DR: the crypto design holds up but the batch client has no failure model, the tx-count and SOL-cost claims in brief.md undercount the research's own numbers, and the six-week plan budgets zero time for hand-encoding Token-2022 confidential instructions in Pinocchio. Cut stealth mode from the demo path if week 2 spikes don't close these gaps.

How to read: **[verified]** checked live or against source; **[likely]** strong evidence, not directly checked; **[open]** unknown, needs a spike.

## Critical

**1. No batch state machine, no idempotency key, no resume path.**
Target: design.md "One payout run" table, plan.md phase 1-2 exit criterion ("N-recipient run works"). A run of N=50 stealth payments is ~7 payer-side transactions each (open, announce, configure, 3 proof-ctx, fund — from `2026-09-11-token2022-mechanics-verified.md`'s 12-step sequence, steps 1-7), so ~350 payer-side transactions, not counting recipient-side sweep. Nothing in design.md names what the client persists between transactions or how it detects "did open land, did configure land, is E already used." A dropped tx, blockhash expiry (150 blocks ≈ 60-90s — routine in a 350-tx run at any realistic send rate), or a crash mid-run leaves a StealthAccount in an unnamed intermediate state (design.md's account table lists no explicit state enum, only "state: opened → configured → funded → swept"). A `fund` retried after a first `fund` actually landed double-funds (design.md guards fund with "once: state must be configured" — good, that guard exists — but the *client* still needs to know it landed before deciding whether to retry, which means it must read account state before every retry, which none of the docs specify). **Fix**: before any batch code, write a client-side ledger (E → {opened_sig, configured_sig, funded_sig} | null) keyed by ephemeral pubkey, checked against on-chain state before each step; treat every step as "check state, then act," never "assume last action failed." Cheap and necessary regardless of language.

**2. Cost claims in brief.md and design.md undercount the project's own research.**
Target: brief.md §6 and §10 ("~10 transactions and ~0.013 SOL per stealth payment"), design.md §Costs ("stealth ≈ 10-11 txs across both sides"). `2026-09-11-token2022-mechanics-verified.md` [verified against Token-2022 source] counts 12 transactions for one stealth payment's full lifecycle (open, announce, configure, 3× proof-ctx for funding, fund+closes, apply-pending, 3× proof-ctx for sweep, sweep+close) and separately gives rent as 0.0127 SOL locked / 0.0042 SOL standing — the SOL figure survived into the brief correctly, the tx-count figure did not (rounded from 12 down to "10-11" with no stated reason). Neither figure includes priority fees or the base fee for multiple signers on some steps (sweep needs P's own signature plus possibly a fee-payer). At N=1000 a 2-tx undercount per payment is 2,000 missing transactions from any duration/cost estimate. **Fix**: replace "~10 tx / 0.013 SOL" with the research's own 12 tx / 0.0127 SOL (locked) + 0.0042 SOL (standing) everywhere it's cited, and add a line item for base fees (12 tx × 5,000 lamports × N, ≈0.003 SOL at N=50, ≈0.06 SOL at N=1000 — small but non-zero) and an [open] line for priority fees, addressed in finding 3.

**3. Priority fees are not in any cost model, and CU per proof-heavy instruction is high enough that they won't stay negligible.**
Target: brief.md §6, design.md §Costs. A live check today (2026-09-14) of `getRecentPrioritizationFees` against mainnet Token-2022 and the unfiltered set both returned 0 across the sampled slots [verified, point-in-time only — this endpoint reports a noisy per-slot minimum-to-land figure, not a reliable "current level," and public RPC sampling windows are short]. That 0 is not proof the design is fee-safe: range-proof verification alone is ~200,000 CU (research: token2022-mechanics-verified), and during any congestion spike a landing priority fee of even 10,000-50,000 microlamports/CU turns one heavy instruction into 0.002-0.01 SOL, which is 15-80% of the entire "0.0127 SOL locked" estimate — on top of it, not instead of it. The plan has no fallback (fixed-fee client, or priority-fee bidding with a cap and retry-with-backoff) if a payment's transactions start failing to land under congestion mid-batch. **Fix (spike, week 1)**: pull `getRecentPrioritizationFees` for Token-2022 and the ZK ElGamal proof program over a real multi-day window (not a single sample) to get a distribution, and build the batch client's fee logic around p75 with a hard per-tx cap and a "pause and alert" behavior in a run, not silent retries that burn dust (see finding 4).

**4. Sweep dust is unbudgeted and can enter a death spiral.**
Target: design.md's `open` instruction ("also funds P's system account with fee dust") and decisions.md's 2026-09-14 entry (P pays its own fee from dust, no relayer). The dust must cover not just the sweep transaction's base fee but, per the same decisions entry, sweeping "always to a fresh self-owned account" — which needs its own rent-exempt token account (≈0.00416 SOL) plus a `ConfigureAccount` step with its own `PubkeyValidityProof` context account (≈0.00134 SOL, reclaimable) before it can even receive the swept balance, plus that transfer's own proof stack if it's a confidential-to-confidential move. "A little SOL...so P can pay the sweep fee" (design.md) describes covering one fee, not the ≈0.02+ SOL a full destination-account setup costs. Worse: if a sweep transaction lands but fails (e.g., dust insufficient for the prevailing priority fee), the fee is still deducted from P — this is not a "free retry," each landed-but-failed attempt shrinks the remaining dust, and there's no stated minimum-dust check before attempting sweep or way to top up P (the recipient has no other key over P; P's key is only known to the recipient via the spend derivation, but P is a program-owned account, not a wallet the recipient can just refill from elsewhere without another payer-shaped transaction). **Fix**: size dust to cover destination-account creation + configure + sweep-fee at a conservative priority-fee assumption (recommend ≥0.02 SOL per stealth payment, not "a little"), and have the client refuse to attempt sweep if P's balance is below a computed floor rather than let it fail on-chain and burn the fee.

**5. Pinocchio has no Token-2022 confidential-transfer instruction builders; this is unbudgeted engineering, not a detail.**
Target: plan.md's week 2-4 rows ("Vault and plain path," "open + configure + fund," "Scan, sweep, close"). `pinocchio-token-2022` (skill ref: programs/pinocchio.md) exposes the base token program surface; nothing in the Pinocchio ecosystem wraps `ConfigureAccount`, `Deposit`, `ApplyPendingBalance`, the split-proof `Transfer`, `Withdraw`, `EmptyAccount`, or `CloseAccount` for the confidential extension the way `spl-token-2022`/`spl-token-client` do for Anchor/native Rust off-chain clients. Every one of those instructions — discriminator, account ordering, proof-location encoding (`ProofLocation::InstructionOffset`), and PDA-signed `invoke_signed` variants — must be hand-encoded against the Token-2022 source by the owner, in both the on-chain program (accounts + CPI) and cross-checked byte-for-byte against whatever builds the client-side transaction. That is the single largest unbudgeted line item in the plan: plan.md's week 2-to-3 row ("Registry; open + configure + fund with ECDH-derived key") reads as one week of work; hand-encoding six CPI instruction builders plus their proof-context plumbing, correctly, is normally its own multi-week effort even with a working Anchor/anchor-spl reference to port from. **Fix**: budget it explicitly (see revised table below) and do not attempt to hand-roll from scratch — port the byte layouts directly from `spl-token-2022`'s instruction module rather than re-deriving them, and cross-check every instruction against a LiteSVM test that also runs the equivalent `spl-token-client` call for a golden-byte comparison.

## Major

**6. Testing stack: Mollusk/LiteSVM support for the ZK ElGamal proof program is asserted nowhere and must be checked before week 1 ends.**
Target: design.md's tech stack line ("LiteSVM + Mollusk, Surfpool, devnet"), plan.md's implicit assumption that unit tests can run the full confidential-transfer flow without a live cluster. The skill's testing.md doc describes LiteSVM/Mollusk as running "your program" plus whatever's loaded, but doesn't confirm the ZK ElGamal proof program (a *native*, not BPF-loaded, program — confirmed live [verified] on both devnet and mainnet today, owner `NativeLoader1111111111111111111111111111111`) is included in either harness's built-in program set by default. If it isn't, every proof-verification instruction in a LiteSVM/Mollusk unit test either no-ops or errors, and the team is pushed onto Surfpool (a full RPC-backed SVM) for anything touching a real proof — much slower feedback loop, and Surfpool's own docs (skill ref confidential-transfers.md) claim confidential transfers currently only work against a separate `zk-edge.surfnet.dev` testnet, which **contradicts** the live on-chain check above showing the program deployed and executable on ordinary devnet/mainnet RPC today. One of these two sources is stale. **Fix (spike, week 1)**: run one `ConfigureAccount` + `PubkeyValidityProof` instruction through LiteSVM and Mollusk directly, and separately through plain `surfpool start --network devnet`, to settle which harnesses actually verify the proof rather than silently skip it. This gates whether week 1-3 unit tests are trustworthy at all.

**7. Codama IDL generation doesn't exist for Pinocchio; the TS client is hand-written by definition.**
Target: design.md tech stack line mentioning Codama, plan.md's assumption that "teammates do TS SDK." Codama's typical input is an Anchor IDL or a Kinobi-style IDL description; a Pinocchio program emits neither natively (no `idl-build` feature, no anchor macros). The team either (a) hand-writes a Codama IDL JSON describing the two programs' instructions/accounts by hand and generates the client from that, or (b) hand-writes the TS client directly with `@solana/kit` codecs. Either way this is teammate-side work with no shortcut from the program side, and the plan doesn't mention it as a deliverable with its own time slot — it's implied to fall out of "TS SDK and demo." **Fix**: pick (a), a hand-written Codama IDL, since it at least gives generated encode/decode and is reusable if instructions change; budget it as its own week-2 task in parallel with the owner's program work, not sequenced after.

**8. Recipient scan at scale needs an indexer the plan doesn't mention, though demo scale (N≤50-1000) is fine on a paid RPC.**
Target: design.md confidence table ("Discovery via program-account filter | high | standard RPC"), brief.md scope ("recipient client: ... scan ..."). `getProgramAccounts` with a `memcmp` filter is disabled or heavily rate-limited on the free public endpoints used for the RPC checks in this review (Solana Labs' own public RPC has documented gPA restrictions); it works on any paid provider (Helius, Triton, QuickNode) at demo scale (10k-100k accounts) but degrades badly past ~1M accounts without a dedicated index, since gPA is a full table scan with no secondary index on `view_tag` server-side beyond the memcmp byte compare. At the capstone's actual scale (tens to low hundreds of stealth accounts for a demo) this is a non-issue; the "high" confidence rating in design.md is only true at that scale and should say so, not read as a general scalability claim. **Fix**: no code change needed for the demo; add one sentence to design.md's confidence table caveat: "high at demo scale (≤1k accounts) on a paid RPC; an indexer becomes necessary above roughly 100k live stealth accounts, out of scope."

## Minor

**9. Lookup tables don't reduce stealth-payment transaction count the way design.md's cost section implies.**
Target: design.md §Costs ("Batching amortises client proof generation and lets the run use lookup tables"). The binding constraint on splitting a confidential Transfer into 5+ transactions is the ~1232-byte transaction size limit against the *proof data payload* (a range proof alone is ~1.4KB, per research), not account-reference bytes. A lookup table shrinks 32-byte account pubkeys to 1-byte indices, which helps pack more *instructions* per transaction only when the limiting factor is account count, not proof size. For this design LUTs help batch multiple *plain* transfers' non-proof instructions together, or shrink the transaction carrying the final `Transfer` call itself, but will not collapse the 12-tx-per-stealth-payment sequence. **Fix**: rephrase the design.md line to "lookup tables reduce per-tx account overhead on the transfer and close instructions; they do not reduce the proof-context transaction count," so the team doesn't plan around a tx-count reduction that won't happen.

**10. Devnet ZK ElGamal proof program is live; airdrop limits are the real week-1-6 risk, not program availability.**
Target: plan.md risk table ("Token-2022 confidential program disabled again... demo blocked"). Live check today [verified, 2026-09-14]: the ZK ElGamal proof program account exists and is `executable: true` on both `api.devnet.solana.com` and `api.mainnet-beta.solana.com`. The 2025-2026 disablement precedent plan.md cites is a real risk category but not the current state — so the mitigation ("LiteSVM tests as fallback demo") is solving a smaller problem than the actual one, which is devnet's shared faucet: a single N=50 run needs on the order of 0.6-1 SOL held/locked across the run (finding 2's numbers) plus dust per finding 4, and the standard devnet airdrop is capped per request and per IP/day and is routinely drained during hackathon-adjacent periods. **Fix**: fund a devnet wallet early via a bridge or a teammate's mainnet-to-devnet path is not available (devnet SOL has no bridge from mainnet); request airdrops incrementally across week 1-2 rather than in one week-6 burst, and keep a LiteSVM/Surfpool-only fallback demo path regardless, since it removes the faucet dependency entirely.

## Six-week plan (revised)

| Week | Phase | Exit criterion |

| 5 | Adversarial tests (dropped tx, double-fund, half-open, priority-fee spike simulated via Surfpool); benchmarks at N=50; auditor decrypt demo | attacks rejected or explicitly handled; N=50 numbers published, not N=10 extrapolated |
| 6 | Demo hardening, status page, sRFC-42 write-up; N=1000 numbers only if week 5 leaves slack | three-minute terminal demo; N=1000 claim marked [open] if not actually run |

This drops one implicit assumption from the original table: that "stealth account configured and funded" (was week 2-3) can happen before the Pinocchio CT instruction builders exist. It can't — finding 5 has to land first, which is why it's pulled into week 1 alongside the spikes rather than starting fresh in week 2.

## Spikes for week 1

1. **TS vs Rust proof generation, N=1 and N=50.** Generate one full proof set (pubkey-validity, equality, ciphertext-validity, range) in both `solana-zk-sdk` (Rust) and `@solana/zk-sdk` (wasm) on the actual dev laptop; time and memory both. Exit criterion: a number, not a guess — if wasm is >3x slower than native at N=50, the batch client moves to Rust and "teammates do TS SDK" shrinks to the non-proof-generation parts of the SDK.
2. **LiteSVM/Mollusk vs Surfpool proof verification.** Run one `ConfigureAccount` + `PubkeyValidityProof` through each harness (finding 6). Exit criterion: which harness(es) actually verify the proof rather than silently pass; that decides the week-2+ test loop.
3. **Dust-sizing dry run.** On LiteSVM, simulate open → configure → fund → sweep-to-fresh-account → close with a range of dust amounts and current representative priority fees (from spike 4). Exit criterion: minimum dust that survives one retry under a simulated fee spike (finding 4).
4. **Real priority-fee distribution.** Pull `getRecentPrioritizationFees` for Token-2022 and the ZK proof program over several days, not one sample (finding 3). Exit criterion: a p50/p75/p95 number to put in the cost model instead of "priority fees at current mainnet levels."
5. **Devnet gPA memcmp check on the RPC provider the team will actually use.** Confirm it's allowed and get a real latency number for a few hundred accounts (finding 8). Exit criterion: confirmed working provider + latency, or decision to defer scan-at-scale entirely to "out of scope for capstone."

## Brief refinements

These follow from the findings above; brief.md is not frozen, so proposing wording rather than softening the finding to fit it.

- §6 Limitations, cost bullet. Current: "About 0.013 SOL locked per payment until close [likely]. Batching amortises proof work, not transaction count." Proposed: "About 0.0127 SOL locked per payment until close, 0.0042 SOL standing after close, across 12 transactions (not ~10) [likely, research: token2022-mechanics-verified]. Priority fees are not included and are [open] pending a week-1 measurement; batching amortises client-side proof generation, not transaction count or fees."
- §10 Claims table, last row. Current: "~10 transactions and ~0.013 SOL per stealth payment | likely | token2022-mechanics-verified." Proposed: "~12 transactions and ~0.0127 SOL locked (0.0042 standing) per stealth payment, excluding priority fees | likely | token2022-mechanics-verified." The research file already supports the corrected number; only the brief needs to catch up.
- §7 Scope, "Do not build" list. Add a line: "An indexer for stealth-account discovery beyond demo scale (findings: arch-r1-ops-cost-skeptic, #8). Scan at demo scale (≤1k accounts) uses a paid RPC's getProgramAccounts, not a custom index." This makes explicit a scope boundary the current list is silent on.
- §6, sweep/dust bullet (new). The "Payer holds that one account's key" bullet should get a companion line: "Dust sizing: the payer funds P with enough SOL to cover the destination account's rent, configure-proof rent, and sweep fee under a conservative priority-fee assumption, not a token amount. Underfunding strands the payment; the client refuses to attempt sweep below a computed floor." This is a design correction the brief's current wording doesn't surface at all.
- plan.md open questions (Q7). Current text measures "batch size before lookup tables and proof staging become the bottleneck" — proposed addition: the correct framing is proof-context transaction count and priority-fee exposure, not lookup tables (finding 9); LUTs are not the lever this question implies.
