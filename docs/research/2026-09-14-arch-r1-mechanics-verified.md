# Arch R1 — Pinocchio-era mechanics re-verification (source-verified, 2026-09-14)

TL;DR: the PDA-owner design still holds end to end (no CT instruction requires the token account itself to sign, confirmed in both the processor source and the interface crate) and inline proof offsets actually work fine under CPI, so design.md's reason for avoiding them is a preference, not a technical wall. No Pinocchio crate builds confidential-transfer instructions yet, so the stealth program hand-encodes them against the raw interface discriminants below.

Sources: spl-token-2022-interface 3.1.1 and 2.1.0, solana-zk-elgamal-proof-interface 0.1.3, solana-zk-elgamal-proof-program 3.1.14, solana-zk-sdk-pod 0.1.2, spl-token-confidential-transfer-proof-extraction 0.6.1 (all from local cargo registry cache), pinocchio 0.11.1 + solana-instruction-view 2.1.0 (local cache), solana-program/token-2022 `main` @ cbd1ce3 (processor.rs), anza-xyz/solana-sdk (instructions-sysvar, transaction, signature crates), anza-xyz/svm (transaction-context), anza-xyz/agave `master` (program-runtime and programs/zk-elgamal-proof), crates.io and npm registry API, docs.rs, GitHub search for anza-xyz/pinocchio PRs and anza-xyz/solana-sdk#819.

## Discriminants and instruction data (source: `spl-token-2022-interface-3.1.1`)

Outer `TokenInstruction::ConfidentialTransferExtension = 27` (`src/instruction.rs:592,1116`). Inner `ConfidentialTransferInstruction` (`repr(u8)`, sequential, `extension/confidential_transfer/instruction.rs:34`): `InitializeMint`=0, `UpdateMint`=1, `ConfigureAccount`=2, `ApproveAccount`=3, `EmptyAccount`=4, `Deposit`=5, `Withdraw`=6, `Transfer`=7, `ApplyPendingBalance`=8, `EnableConfidentialCredits`=9, `DisableConfidentialCredits`=10, `EnableNonConfidentialCredits`=11, `DisableNonConfidentialCredits`=12, `TransferWithFee`=13, `ConfigureAccountWithRegistry`=14. Every CT instruction is dispatched as `[27, <inner discriminant>, ...instruction-specific bytes]` — so ConfigureAccount is `[27, 2, ...]`, ApplyPendingBalance `[27, 8, ...]`, Transfer `[27, 7, ...]`, EmptyAccount `[27, 4, ...]`.

`ProofInstruction` (`repr(u8)`, `solana-zk-elgamal-proof-interface-0.1.3/src/instruction.rs`): `CloseContextState`=0, `VerifyZeroCiphertext`=1, `VerifyCiphertextCiphertextEquality`=2, `VerifyCiphertextCommitmentEquality`=3, `VerifyPubkeyValidity`=4, `VerifyPercentageWithCap`=5, `VerifyBatchedRangeProofU64`=6, `VerifyBatchedRangeProofU128`=7, `VerifyBatchedRangeProofU256`=8, `VerifyGroupedCiphertext2HandlesValidity`=9, `VerifyBatchedGroupedCiphertext2HandlesValidity`=10, `VerifyGroupedCiphertext3HandlesValidity`=11, `VerifyBatchedGroupedCiphertext3HandlesValidity`=12.

`ProofLocation<T>` (`spl-token-confidential-transfer-proof-extraction-0.6.1/src/instruction.rs:53-58`): `InstructionOffset(NonZeroI8, &T)` or `ContextStateAccount(&Address)`. A context-state account is passed as a plain readonly `AccountMeta` in the consuming instruction's own account list (e.g. account #2 of `ConfigureAccount`, accounts #5-7 of `Transfer`) — no separate authority account is passed to the consuming instruction; the authority lives inside the context account's own header (`ProofContextStateMeta.context_state_authority`) and is only checked on close.

Example data layouts: `ConfigureAccountInstructionData` = `decryptable_zero_balance` (36B AE ciphertext) + `maximum_pending_balance_credit_counter` (8B `U64`) + `proof_instruction_offset` (1B `i8`) = 45B (+2 discriminant bytes = 47B total). `TransferInstructionData` = `new_source_decryptable_available_balance` (36B) + `transfer_amount_auditor_ciphertext_lo`/`_hi` (64B each) + 3× `i8` proof offsets (3B) = 167B (+2 discriminant bytes = 169B). Full field layouts for `EmptyAccount`, `Deposit`, `Withdraw`, `ApplyPendingBalance` are in the same file and follow the same `Pod`-struct pattern; not transcribed field-by-field here.

## Consequences for the design

- design.md's Tech stack line still says "Rust + Anchor 1.x" — wrong given the Pinocchio decision, needs updating separately from this pass.
- No Pinocchio crate builds CT instructions (claim 2): the stealth program hand-encodes `ConfigureAccount`/`ApplyPendingBalance`/`Transfer`/`EmptyAccount` against the raw discriminants and `Pod` structs above, and builds `ProofLocation::ContextStateAccount` metas itself. `pinocchio-token-2022` PR #332 worth tracking, not worth waiting for.
- crypto.md's zk-sdk pin is one minor behind current (7.0.1 vs 8.0.0) — update the reviewer checklist's version-recheck item.
- design.md overstates the reason for context-state-only proofs: "offsets are relative to top-level instructions" is accurate mechanically but doesn't itself force context-state-only (claim 3, now fully VERIFIED against runtime source, not PARTLY) — it's a robustness choice, say so.
- Claim 7 headline: the ZK ElGamal proof program is live on mainnet-beta again. Nothing in design.md assumed otherwise, but the `solana-dev` skill's confidential-transfers reference is stale and should be fixed outside this repo.
- Claim 8 account-count question is fully resolved: the binding ceiling is agave's `MAX_TX_ACCOUNT_LOCKS = 128`, not Pinocchio's internal 255-slot buffer. Not a real constraint for this design either way.
- Confidence-table entries for "no on-curve check," "CU/tx-count," and "sweep as tx signer" can move to high given the exact citations above; only the Token-2022 program-side CU overhead (~31k) remains an estimate.
- **Time-sensitive watch item:** a legacy/v0 transaction byte-size increase (1232B to 4096B, SIMD-0296/SIMD-0385) is reported targeted for mainnet around epoch 1035, on or about 2026-09-15 — essentially today. Found via WebSearch summaries only, not confirmed against Agave source (see Could not verify). If active, it changes claim 4's split-transaction conclusion and design.md's Costs-section transaction-count estimates. Re-check before trusting the current 5-transactions-per-Transfer figure.
