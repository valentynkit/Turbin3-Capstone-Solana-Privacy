# Arch R5 — ownership handover to the one-time key (source-verified, 2026-09-14)

TL;DR: SetAuthority(AccountOwner) works exactly as the proposal needs and touches nothing in the ConfidentialTransferAccount extension, so the handover itself is sound; the real cost is that the program stops being able to close the StealthAccount announcement PDA as part of the sweep, because that PDA is program-owned and only the program can debit it. Ten questions checked: 9 VERIFIED, 1 PARTLY (Q10, scope mismatch not a contradiction).

Sources: `solana-program/token-2022` `main`, fetched 2026-09-14: `program/src/processor.rs` (10,155 lines, `process_set_authority` at line 709, `validate_owner` at line 2253, `process_close_account` at line 1298), `program/src/extension/confidential_transfer/processor.rs` (1,465 lines: `process_configure_account` 221, `process_empty_account` 352, `process_transfer`/`process_source_for_transfer` 628/848, `process_apply_pending_balance` 1196, `process_allow_non_confidential_credits` 1281), `interface/src/extension/confidential_transfer/mod.rs`. `spl-token-2022-interface` 3.1.1, local cache, `src/extension/confidential_transfer/mod.rs` and `src/instruction.rs` (`AuthorityType` enum). `solana-program/associated-token-account` `master`, fetched 2026-09-14, `program/src/processor.rs` (`InitializeImmutableOwner` CPI at line 135). ## Consequences for design.md if adopted

Disappears from `sweep`: the program-driven CPI chain `ApplyPendingBalance -> Transfer -> EmptyAccount -> CloseAccount` (Token-2022, via `invoke_signed`). All four become top-level instructions in the recipient's transaction, signed directly by P, with no program in the CPI stack for them.

Appears in `open`: one more CPI, `SetAuthority(AccountOwner, new_authority = P)`, issued by the program right after `ConfigureAccount`/`DisableNonConfidentialCredits`, while the PDA is still the owner and can sign it via `invoke_signed`. `open` must also drop `InitializeImmutableOwner` from its CPI list — Q1b shows SetAuthority(AccountOwner) is a hard failure if that extension is present, and design.md's current account layout row explicitly lists `ImmutableOwner + ConfidentialTransferAccount`, so that layout needs to change under this proposal.

The recipient's transaction becomes: `create D` (unchanged) -> proofs -> `ApplyPendingBalance`, `Transfer`, `EmptyAccount`, `CloseAccount` as four top-level Token-2022 instructions signed by P, drain of P's lamports to `drain_to` -> and, per the next paragraph, a call into the program to close the StealthAccount PDA. Atomicity is unaffected: a single Solana transaction is atomic regardless of whether its instructions are top-level or CPI'd through one program, so design.md's "no transaction boundary for dust to land in" argument (line 81) holds exactly the same way under handover — that argument was never actually about CPI, only about instruction ordering within one transaction, and this change makes that visible.

What the announcement account still needs: the StealthAccount PDA is owned by *this program*, not Token-2022, and only the owning program can debit its lamports (direct lamport manipulation on a program-owned account requires that program to be the one executing). Under full handover, the recipient's transaction still needs at least one call into the program — a small "close_announcement" or equivalent instruction, signed by P, that closes StealthAccount and refunds it to `payer` — even though the program is no longer touching Token-2022 at all. So "no program call" in the sweep is not fully achievable while StealthAccount stays a program-owned PDA; the program's involvement shrinks from four CPI'd Token-2022 calls plus the PDA close to just the PDA close.

Net effect on the confidence table (design.md lines 130-135): the "PDA-owned confidential account; program-signed configure, apply, transfer, empty, close" row would need to split in two — configure stays program-signed (unchanged), but apply/transfer/empty/close move to P-signed top-level instructions, and a new small program instruction appears for closing the announcement.

## Overall verdict

REFUTED: none. PARTLY: Q10 only (scope mismatch between sRFC-42's plain-SPL stealth addresses and this design's confidential-balance custody, not a contradiction). Every other claim in the proposal VERIFIED against current `main` source — the handover mechanic is sound, but it does not fully eliminate the program from the recipient's transaction, because the StealthAccount announcement PDA still needs the program to close it.
