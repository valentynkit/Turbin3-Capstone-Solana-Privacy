# R2 — adversarial crypto/privacy review of the candidate (2026-09-14)

TL;DR: atomic open+configure+fund genuinely kills the original C1 (pre-funding confidential-dust griefing), but two source-verified siblings replace it: a non-confidential SPL transfer into the account's public balance, and a confidential dust credit landed after sweep's `ApplyPendingBalance` resets the counter — both permanently block `close` and neither has a recovery instruction. Separately, the sweep destination D is not a safe place to spend from: the payer sees it in the public sweep transaction and can watch it forever, so the design needs one more hop before it matches its own privacy claim.

Sources read for this pass, beyond the assigned docs: `solana-program/token-2022` `main`, `program/src/extension/confidential_transfer/processor.rs` and `interface/src/extension/confidential_transfer/mod.rs` (the state struct moved out of `program/` into `interface/` since the 09-11 review — same logic, new path), `program/src/processor.rs` (`process_close_account`, `process_transfer`), and `anza-xyz/solana-sdk` `curve25519/src/edwards.rs` plus `agave` `compute-budget/src/compute_budget.rs` for syscall costs.

## CRITICAL

**A. A plain non-confidential SPL transfer into the token account's public balance permanently blocks `close`, and atomic funding does nothing to stop it.** [verified]
Target: candidate's `open` row and the "no public window" claim under "The payer's one transaction."
`process_configure_account` (interface `mod.rs:295-304`) sets `allow_confidential_credits = true` **and** `allow_non_confidential_credits = true` unconditionally — there is no way to configure an account with non-confidential credits pre-disabled. `process_transfer` (base `processor.rs:533-537`) only checks `non_confidential_transfer_allowed()` on the destination, which passes as long as that flag is true; a base `Transfer`/`TransferChecked` into a same-mint account requires no destination signature at all and never touches `pending_balance_credit_counter`. So anyone watching `getProgramAccounts` for a freshly created token account of a target mint can send it one base unit any time — before, during, or long after the atomic `open` transaction — and it lands, unauthenticated, in `token_account.base.amount`. `process_close_account` (`processor.rs:1314-1316`) then rejects `CloseAccount` with `NonNativeHasBalance` whenever `amount != 0`. Nothing in the candidate's five instructions moves tokens out of the public balance (`Deposit` would, but it isn't wired into `sweep` or `close`, and even if it were it collides with finding B below). The account and its rent are stuck forever for the price of one lowest-denomination unit.
Cheapest fix: add a sixth CPI to `open`, right after `ConfigureAccount`, calling `DisableNonConfidentialCredits` (discriminant `[27, 12]`) on the new token account with the stealth PDA signing. It costs nothing extra in proof bytes (no ZK proof needed for this instruction) and, because it lands inside the same atomic transaction as the other guards, closes the vector as completely as the counter fix closed the original C1.

**B. Sweep's own `ApplyPendingBalance` reopens the one-shot credit counter, and `close` has no instruction to clear what lands in that window.** [verified]
Target: candidate's `close` row ("state Swept" guard) and R2-1 in the open-questions table.
`process_apply_pending_balance` (`ct_processor.rs:1235-1241`) unconditionally resets `pending_balance_credit_counter` to 0 when it merges pending into available — it does not check `expected_pending_balance_credit_counter` against anything, it just records both fields for off-chain bookkeeping. `sweep` runs `ApplyPendingBalance` then `Transfer`, so the instant `ApplyPendingBalance` completes, the account's counter is 0 again with `maximum = 1` still in force: one more confidential credit (or one non-confidential credit, per finding A) is now legal. A griefer who dusts the account in the gap between `sweep` and `close` — two separate transactions in the candidate's own flow — lands a credit in `pending_balance_lo/hi`. `closable()` (`interface mod.rs:127-135`) requires `pending_lo`, `pending_hi`, **and** `available_balance` all zero; `EmptyAccount` only zeroes `available_balance`. The candidate's `close` instruction is `EmptyAccount` + `CloseAccount`, with no `ApplyPendingBalance` step, so a post-sweep dust credit makes `closable()` fail forever. There is no instruction in the program that can reach this state and fix it: `sweep`'s state guard is "Live," so it cannot be called again once `Swept`. This directly answers R2-1's second half: no, an account with nonzero pending balance cannot be emptied and closed by this program as specified, and the "state Swept" guard is not sufficient — it prevents double-sweeping the funds but does not prevent this specific post-sweep DoS.
Cheapest fix: make `close` do `ApplyPendingBalance` (with `expected` read live, `new_decryptable_available_balance` recomputed) then `EmptyAccount` then `CloseAccount`, all PDA-signed, all in one transaction — cheap, no proof needed for `ApplyPendingBalance`. Combined with finding A's fix this closes the credit window on both instructions where it can reopen.

## MAJOR

**C. The payer learns D from the public sweep transaction and can watch it forever; the candidate's own recommended flow spends from that same address.** [likely]
Target: privacy.md's "Sweep to a fresh self-owned account" row and the candidate's four-transaction recipient sweep sequence.
`sweep`'s `Transfer` instruction lists `destination` in cleartext account metadata — that's true of every Solana instruction regardless of confidential amounts. The payer does not need to be "a chain observer" to find this: it already knows E and P from having created them in its own `open` transaction, so finding the matching `sweep` and reading off D costs it nothing. From then on the payer can watch every future plaintext-visible thing D does: other program interactions, other transfers it signs, any KYC'd exchange deposit it eventually makes. privacy.md's artifact table marks this row "no" under "Links to recipient without b_scan" — true for a generic observer, false for this specific payer, who never needed b_scan in the first place. `crypto.md`'s stated mitigation ("sweeps go to a fresh self-owned account before any spend") does not address this: fresh-and-unused-by-other-payments is not fresh-and-unknown-to-this-payer. If the recipient's client (or a human) later spends directly from D, exactly the deanonymization the whole construction exists to prevent happens for that one payer, just delayed by however long the recipient waits.
Cheapest fix: document D as a burned address, same tier as the stealth account itself — never spend from it. The client's `close` and `sweep` commands should chain automatically into a second, unrelated hop (a plain transfer from D to the recipient's real spending wallet, ideally batched with unrelated traffic or time-delayed) before D is considered safe to abandon. Update privacy.md's row to read "no, for a generic observer; yes, for the paying party, until the recipient moves funds again" and remove the implication that spending from D is the end state.

## MINOR / NOTE

**D1. Torsion-free `B_spend` is fully checkable on-chain, cheaply — the candidate's claim holds and beats its own hedge.** [verified]
`solana-sdk` `curve25519/src/edwards.rs` exposes `multiply_edwards(scalar, point)` as a syscall (not just `validate_edwards`), and `compute_budget.rs:220-223` prices `curve25519_edwards_validate_point_cost` at 159 CU and `curve25519_edwards_multiply_cost` at 2,177 CU. Multiplying the candidate point by the group order L and checking the result equals the identity is the correct general torsion-free test — a cheaper "reject the 8 known low-order encodings" table lookup only catches pure-torsion points and misses points with a nonzero torsion component riding on top of a nonzero prime-order component, so it should not be substituted for the multiply-by-L check. At ~2,336 CU total (validate + multiply) this is negligible against a 1.4M budget. No fix needed; worth pinning "multiply by L, not blacklist the 8 points" explicitly in crypto.md's reviewer checklist so a future implementer doesn't take the cheaper-looking shortcut.

**D2. R2-7 (check P on-curve) is cheap enough that "only burns the payer's own money" is not a reason to skip it.** [note]
`validate_edwards` costs 159 CU. Given `open` already pays for one `VerifyPubkeyValidity` proof and several CPIs, adding a 159 CU on-curve check on P is free relative to the transaction's own budget and turns a silent, wasted transaction into an explicit error. Recommend yes.

**D3. The disclosure receipt does not leak beyond the one payment, contingent on the still-open HKDF independence review.** [likely]
`{E, k, ct_ikm}` discloses the leaf Expand output only, never `S` or `PRK` — the auditor cannot walk back to `t`, the view tag, or the nonce seed without inverting HKDF-Expand (a PRF, assumed one-way). Because v1 uses one `E` per payment (the per-run `E` idea is explicitly deferred), each payment has an independent `S` and therefore an independent `PRK`, so disclosure composes safely across payments even before the per-run design lands: there is no shared root to leak into. This is sound only as far as M5's underlying independence assumption holds, which is still an open external review item, not new to R2.

**D4. `k` is currently dead weight in the receipt and the announcement — cheap to fix now, expensive to fix later.** [verified against candidate's own schema]
StealthAccount's PDA seed is `["stealth", E]`; `k` appears nowhere in it, and `k` is not needed to verify a disclosure receipt since `ct_ikm` is disclosed directly rather than recomputed from a label. In v1, `k` is always 0 and does no work. That's fine as a placeholder, but the day the deferred per-run-`E` design ships, the PDA seed must become `["stealth", E, k]` — a breaking account-address change, not an additive one. Cheapest fix: put `k` in the seed today (`["stealth", E, k]` with `k = 0` for everyone in v1), costing nothing now, so the future extension is additive instead of a migration.

## What survived

- The exact class of griefing C1 named (unauthenticated third-party crediting before the recipient can act) is real and still live in the candidate, just relocated to two other instructions — not eliminated by "atomic funding," contrary to the candidate's own framing.
- Payer cannot forge a sweep and cannot decrypt the destination side of the outgoing transfer: unchanged, no new attack found against the tweak/nonce separation.
- Fresh D and fresh D_owner per payment, if the client actually enforces "fresh," structurally block cross-payment correlation through P without b_scan — the residual is the single payer of each payment watching its own D, not cross-payer correlation.
- The derivation tree's domain separation still holds up against the disclosure receipt; nothing in the receipt format itself creates a new leak.
