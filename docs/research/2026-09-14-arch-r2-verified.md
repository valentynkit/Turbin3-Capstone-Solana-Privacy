# Arch R2 — candidate v1 verification (source-verified, 2026-09-14)

TL;DR: the credit-counter and close mechanics hold as the candidate assumed, the fee payer can legally drain to zero, and the combined per-recipient transaction fits well under 1232 bytes even without a lookup table. Two real corrections: `ApplyPendingBalance`'s expected-counter field is not enforced by the program (client-only bookkeeping), and PYUSD/USDG both ship `auto_approve_new_accounts: false`, which the candidate's own gating rule turns into a no-go without more plumbing.

Sources: Token-2022 `main`@ processor.rs (`process_transfer`/`valid_as_destination`, `process_empty_account`, `process_apply_pending_balance`) via raw.githubusercontent.com; `spl-token-2022-interface` 3.1.1 (local cache, account-meta builders); `solana-zk-elgamal-proof-interface` 0.1.3 and `solana-zk-elgamal-proof-program` 3.1.14 (local cache); `spl-token-confidential-transfer-proof-extraction` 0.6.1 (local cache); `anza-xyz/agave` `master` `svm/src/account_loader.rs`, `svm/src/rent_calculator.rs`, `svm/src/transaction_account_state_info.rs`; `solana-program/address-lookup-table` `master` `program/src/processor.rs`, `solana-address-lookup-table-interface` 3.2.0 (local cache) `state.rs`; `litesvm` 0.10.0 (local cache) `src/lib.rs`; `anza-xyz/mollusk` `main` `harness/src/program.rs`; `solana-builtins` 3.1.14 (local cache) `src/lib.rs`; `agave-feature-set` 3.1.14 (local cache); `solana-zk-sdk` 8.0.0 crate tarball from crates.io, `src/encryption/derivation.rs`; solana-foundation/solana-improvement-documents `0296-larger-transactions.md` and `0385-transaction-v1.md`; mainnet-beta and devnet RPC `getAccountInfo` on the transaction-v1 feature account and on USDC/PYUSD/USDG mints.

## Consequences for candidate v1

- **`auto_approve_new_accounts: false` on both PYUSD and USDG (R2-6).** The candidate's "Mint policy" row says stealth-mode go/no-go depends on this flag, but doesn't say what "no" means operationally. With it false, `ConfigureAccount` alone does not make a confidential account usable — the mint authority must also call `ApproveAccount` (discriminant 3, not currently in the candidate's instruction list) before the account can transact. As designed, the payer's one-transaction stealth flow (open + fund in one atomic tx) cannot work unmodified on either PYUSD or USDG: a third party's approval step sits between configure and the funding transfer, which reopens exactly the "public window between configure and fund" gap that section "The payer's one transaction per stealth recipient" says doesn't exist. USDC isn't Token-2022 at all, so it's out of scope regardless. This needs a design answer, not just a probe-and-flag.
- **R2-1d contradicts an assumption embedded in the candidate's account layout.** `StealthAccount`/token-account rent-refund and close flow don't depend on `ApplyPendingBalance`'s expected-counter matching, so nothing breaks mechanically, but any client code that treats a mismatch as an error (rather than "more to apply") will misbehave — the program will never reject it, so this has to be handled client-side as documented, not assumed to be enforced on-chain.
- **R2-2/SIMD-0385: v1 transactions drop lookup table support entirely.** The candidate's per-run lookup table strategy and the hoped-for "1 to 2 tx if the 4096-byte transaction size is active" line are in tension: getting the larger 4096-byte envelope means giving up ALT compression, not stacking on top of it. Given R2-3 shows the current per-recipient tx already fits in legacy format with margin to spare, the real win from v1 (once live) is folding the three proof-context-creation transactions into the same transaction as `open`+`Transfer`, not shrinking the existing combined tx further. That's a different design question from what the candidate frames, and the feature isn't live on mainnet-beta yet as of this check.
- **R2-4 removes a stated cost-model risk.** The candidate's contested question "R2-4: otherwise 0.00089 SOL strands per payment" is resolved: the fee payer can legally end at exactly zero lamports whether via fee deduction or an in-transaction transfer. The "Money on P" section's dust math doesn't need a floor reserved against this failure mode.
- **R2-5 changes the Mollusk setup, not just a config flag.** The candidate's testing section says "Mollusk for CU benches" without qualification; Mollusk needs the `all-builtins` Cargo feature turned on for both `zk_elgamal_proof_program` and `compute_budget_program` (the latter matters because `SetComputeUnitLimit` appears in nearly every transaction in this design) — without it, CU benches involving either won't run at all, they'll fail to find the program.
- **R2-7 is a correction to the open question, not a new risk.** The candidate's R2-8 open question asked whether P (a system account) is a valid authority for contexts consumed by a PDA-owned CPI. The real answer is that authority is irrelevant to consumption — only to closing, which is a separate concern the design already handles correctly (P creates and closes its own contexts).

## Could not verify

- Whether LiteSVM's or Surfpool's current release specifically handles v1 (SIMD-0385) transactions — not checked against either's transaction-parsing source. Given the mainnet feature isn't active yet, this is lower priority, but should be rechecked once the candidate actually depends on v1.
- Surfpool's own SVM/builtin-loading source was not read directly; the R2-5 verdict for Surfpool rests on documented default-network behavior plus the general mainnet-fork premise, not a line-level citation like the LiteSVM and Mollusk verdicts have.
- The `open` instruction's real account list and instruction data size (R2-3) — this report used an estimate (9 accounts, 110B) consistent with the candidate's account descriptions, but the instruction has not been written. A spike should re-run the byte count once the actual encoder exists.
- Whether `ApproveAccount` needs to be added to the candidate's instruction set to handle `auto_approve_new_accounts: false` mints, and what that does to the atomicity claim in "The payer's one transaction per stealth recipient" — this needs a design decision, not just a source check.
